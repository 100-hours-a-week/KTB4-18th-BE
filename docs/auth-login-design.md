# 이메일·비밀번호 로그인 백엔드 설계

> 대상 브랜치: `feature/auth-login` · 기준 커밋: `origin/dev` · 영역: Backend

## 1. 목적과 사용자 결과

- 해결하려는 문제: 가입한 사용자가 이메일과 비밀번호로 서비스에 인증할 수 없다.
- 기대 결과: 유효한 자격 증명을 가진 사용자는 access token과 refresh token Cookie를 받아 인증이 필요한 기능을 이용할 수 있다.

### 사용자 시나리오

1. 가입한 사용자가 유효한 이메일과 비밀번호를 제출하면 access token과 refresh token Cookie를 발급받는다.
2. 미가입 이메일, 비밀번호 불일치, 탈퇴 사용자 또는 잠금 상태 사용자는 계정 상태를 식별할 수 없는 동일한 인증 실패 응답을 받는다.
3. 같은 활성 계정에서 인증 실패가 10회 누적될 때마다 잠금 시간이 5분, 10분, 20분, 40분처럼 두 배로 늘어난다.
4. 잠금이 해제된 뒤 정상 로그인에 성공하면 실패 횟수와 잠금 단계가 모두 초기화된다. 다음 잠금은 다시 5분부터 시작한다.

## 2. 범위

### 포함

- `POST /api/v1/auth/login`
- 로그인 요청·응답 DTO와 이메일·비밀번호 요청값 검증
- `users.email` 기반 사용자 조회, BCrypt 해시 비교, `deleted_at` 사용자 차단
- access token 응답 Body 반환 및 refresh token `Set-Cookie` 발급
- 로그인 엔드포인트 비인증 접근과 기존 `SecurityFilterChain` 통합
- 서버 메모리 기반 실패 횟수·잠금 상태 관리 및 시간 제어 테스트
- 공통 400·401·500 응답, API 명세 검토, 코드 리뷰

### 제외

- 회원가입, 토큰 재발급, 로그아웃
- 비밀번호 변경·재설정·이메일/전화번호 인증 API
- 로그인 제한 상태의 DB/ERD/Flyway 변경
- Redis 등 공유 저장소 도입과 로그인 제한 조회 API

## 3. 현재 기준과 선행 조건

`origin/dev`의 `RecommendationSecurityConfig`에는 추천 경로용 체인과 그 외 경로를 인증 요구로 처리하는 체인이 있다. 로그인 경로를 별도 체인으로 추가하거나 기존 체인에 명시적으로 예외를 부여하되, 추천 API의 기존 보안 동작은 유지해야 한다.

현재 `origin/dev`에는 다음 선행 조건이 구현되어 있지 않다.

- 인증 토큰 발급·검증 기반 구현과 해당 이슈 번호
- `users(id, email, password_hash, deleted_at)` 스키마 및 로그인 테스트 데이터

위 항목은 이 기능의 직접 구현 범위가 아니다. 준비 여부를 확인한 뒤 로그인 구현을 시작한다.

## 4. API 계약

### 요청

`POST /api/v1/auth/login`

```json
{
  "email": "name@example.com",
  "password": "password"
}
```

- `email`: 필수, 이메일 형식
- `password`: 필수, 공백만으로 된 값은 허용하지 않음
- 인증이 필요 없는 POST 경로다.

### 성공 응답

HTTP 200, 메시지는 `login success`다.

```json
{
  "message": "login success",
  "data": {
    "access_token": "<access-token>",
    "expires_in": 3600
  }
}
```

- 응답 Body의 data에는 `access_token`, `expires_in`만 포함한다.
- refresh token은 Body, 로그, 예외 메시지에 포함하지 않는다.
- refresh token은 `Set-Cookie`로만 전달한다. 속성은 `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/api/v1/auth`를 사용한다.

### 실패 응답

| 상황 | HTTP | 메시지 | data |
| --- | --- | --- | --- |
| 요청값 누락·형식 오류 | 400 | `invalid request` | `null` |
| 미가입·비밀번호 불일치·탈퇴·잠금 | 401 | `invalid credentials` | `null` |
| 예상하지 못한 오류 | 500 | `internal server error` | `null` |

401 응답은 원인을 구분하지 않는다. 사용자 존재 여부, `deleted_at` 값, 실패 횟수, 잠금 상태는 외부 응답에 노출하지 않는다.

## 5. 처리 흐름

1. 컨트롤러는 요청 DTO를 검증한다. 유효하지 않으면 공통 400 응답을 반환한다.
2. 서비스는 이메일을 정규화한 뒤 메모리 잠금 상태를 먼저 확인한다. 잠금 상태면 동일한 401을 반환한다.
3. 사용자 조회 결과가 없거나 `deleted_at`이 존재하면 인증 실패로 처리한다.
4. BCrypt 비교가 실패하면 실패 상태를 원자적으로 갱신하고 401을 반환한다.
5. 자격 증명이 유효하면 토큰 발급 기반에 access/refresh token 생성을 요청하고 refresh token을 Cookie에 설정한다.
6. 성공 처리에서는 해당 이메일의 메모리 실패 상태 전체를 제거해 실패 횟수와 잠금 단계를 모두 초기화한다. 잠금 상태와 사용자 존재 여부를 응답으로 구분하지 않는다.

## 6. 실패 제한 정책

### 상태 모델

- 키: 이메일. 저장 전 이메일 정규화 규칙은 구현 전에 확정한다.
- 저장 위치: 단일 서버 프로세스 메모리. DB·ERD·Flyway에는 저장하지 않는다.
- 상태: 현재 10회 단위 안의 실패 횟수, 현재 잠금 만료 시각, 누적 잠금 단계.
- 동시성: 동일 이메일의 상태 갱신은 원자적이어야 한다.

### 정책

1. 실패 10회째에 첫 번째 잠금을 설정하고 서버 시간 기준 5분 동안 차단한다.
2. 잠금 해제 뒤 다시 10회 실패하면 두 번째 잠금은 10분, 세 번째는 20분, 네 번째는 40분으로 두 배씩 증가한다.
3. 잠금이 해제된 뒤 정상 로그인에 성공하면 현재 실패 횟수와 누적 잠금 단계를 모두 삭제한다. 다음 10회 실패는 다시 5분 잠금이다.
4. 잠금 중 요청은 실패 횟수나 잠금 시간을 공개하지 않고 401 `invalid credentials`를 반환한다.

### 운영 제약과 결정 필요 사항

- 서버 재시작 시 상태가 사라지고, 다중 인스턴스 환경에서는 인스턴스별로 상태가 분리된다. 이 제약을 테스트 기록과 PR에 남긴다.
- 미가입·탈퇴 이메일은 실패 상태에 기록하지 않는다. 임의 이메일로 메모리 상태를 무한 생성하는 공격을 피하면서, 실제 활성 계정의 비밀번호 추측 시도만 제한한다. 외부 응답은 모두 같은 401로 유지한다.
- 비밀번호 변경 완료 연동은 필요하지 않다. 잠금은 시간 경과로 해제되며, 정상 로그인은 모든 잠금 이력을 초기화한다.
- **결정 필요:** 잠금 시간이 계속 두 배로 증가할 때 적용할 최대 잠금 시간 상한. 현재 요구사항에 따라 상한 없이 단계별 두 배 증가를 적용한다.

## 7. 모듈 설계

구현 시 기존 패키지 구성과 충돌하지 않도록 `auth` 도메인을 경계로 둔다.

| 책임 | 후보 구성 | 역할 |
| --- | --- | --- |
| HTTP 진입점 | `auth.controller` | 요청 검증, HTTP/Cookie 응답 조립 |
| 계약 DTO | `auth.dto.request`, `auth.dto.response` | 요청·성공 응답 타입 |
| 로그인 유스케이스 | `auth.service` | 사용자 검증, 제한 정책, 토큰 발급 오케스트레이션 |
| 사용자 접근 | `user.repository` 또는 선행 사용자 도메인 | 이메일 조회와 탈퇴 상태 확인 |
| 실패 제한 | `auth.loginattempt` | 메모리 상태와 원자적 전이 |
| 보안 설정 | `config` | 로그인 permitAll 및 기존 추천 체인 호환 |
| 오류 매핑 | 공통 예외 처리 영역 | 400·401·500 계약 보장 |

정확한 클래스명과 패키지 배치는 선행 인증·사용자 도메인 구현을 확인한 뒤 기존 구조에 맞춘다. 중복 토큰 모델이나 사용자 엔티티는 이 기능에서 새로 만들지 않는다.

## 8. 작업 이슈와 완료 기준

### 상위 기능 이슈

`[FEATURE] 이메일·비밀번호 로그인 API 제공` (기존 #16 본문 교체안)

- 유효 자격 증명은 200 `login success`와 `access_token`, `expires_in`만 포함한 Body를 반환한다.
- refresh token은 지정된 속성의 Cookie에만 존재한다.
- 요청 오류는 400, 모든 인증 실패는 동일한 401, 예상하지 못한 오류는 공통 500 형식이다.
- 관련 단위·통합 테스트, API 명세 검토, 코드 리뷰를 완료한다.

### 하위 작업 1 — 로그인 자격 증명 검증·토큰 응답·SecurityFilterChain 통합

- 포함: DTO/검증, 사용자 조회, BCrypt 비교, 탈퇴 차단, 공통 400·401·500, 토큰/Cookie 계약, SecurityFilterChain 통합, API 계약 테스트
- 제외: 실패 제한 정책, `users` 테이블 생성, 회원가입·재발급·로그아웃·비밀번호 변경 API
- 완료: 성공 Body·Cookie 분리, 실패 원인 비노출, 추천 API 보안 동작 유지, API·보안 통합 테스트 및 리뷰 완료
- 의존성: 토큰 발급 기반, users 스키마와 테스트 데이터

### 하위 작업 2 — 메모리 기반 로그인 실패 제한 정책

- 포함: 이메일별 메모리 상태, 10회 단위의 지수 백오프 잠금(5·10·20·40분), 정상 로그인 시 전체 초기화, 원자적 갱신, 시간 제어 테스트
- 제외: DB·ERD·Flyway, Redis, 비밀번호 변경·재설정·잠금 조회 API
- 완료: 10번째 실패 시 5분 잠금, 이후 10회 실패 단위마다 잠금 시간이 두 배 증가, 정상 로그인 시 단계가 초기화, 상태가 DB에 기록되지 않음, 재시작·다중 인스턴스 제약 기록
- 의존성: 하위 작업 1 및 최대 잠금 시간 상한 결정

이슈 번호, 담당자, 예상 소요 시간, 관련 PR은 생성·배정 후 연결한다.

## 9. 테스트와 검토

- DTO 검증: 이메일 누락/형식 오류, 비밀번호 누락·공백 값 → 400
- 인증 실패: 미가입, BCrypt 불일치, 탈퇴 사용자, 각 잠금 단계 → 모두 같은 401 Body
- 성공: 토큰 Body 필드가 두 개뿐이며 refresh token이 Cookie에만 존재
- 제한 정책: 각 10번째 실패, 5·10·20·40분 경과, 정상 로그인 후 5분 단계 초기화, 동시 요청, 시간 제어
- 보안: `/api/v1/auth/login`만 비인증 허용되고 추천 API 및 기타 경로의 기존 정책이 유지됨
- 회귀: 기존 추천 API 테스트와 로그인 API 통합 테스트
