# 채팅방별 계정 정원 집계

B3는 방마다 같은 계정을 한 명으로 계산한다. 시작 HEAD는 B2 PR #198이 병합된 `7627b55`이며 작업 브랜치는 `feature/chat-room-account-capacity`다.

## 집계 기준

| 상태 | 입장 정원 점유 | 현재 인원 이벤트 |
| --- | --- | --- |
| 입장 후 연결 대기 예약 | 포함 | 제외 |
| WebSocket 연결 중 | 포함 | 포함 |
| 마지막 연결 종료 후 30초 미만 | 포함 | 제외 |
| 예약·재연결 유예 30초 경계 도달 | 해당 참여 제외 | 제외 |
| 명시적으로 종료한 참여 | 해당 참여 제외 | 제외 |

두 집계 모두 방 안의 사용자 ID를 중복 제거한다. 여러 기기·탭·참여가 있어도 같은 방에서는 1명이다.
동일 계정이 두 방에 참여하면 각 방에서 1명씩 계산한다.
같은 계정의 다른 참여가 연결·예약·유예 상태라면 한 참여를 종료하거나 만료해도 그 방의 자리를 반환하지 않는다.

정원이 25명이어도 그 방에 이미 자리를 가진 계정의 추가 연결은 허용한다.
새로운 계정은 `CHAT_ROOM_CAPACITY_EXCEEDED`로 거절한다.
유예가 끝난 계정은 기존 DB membership이 남아 있어도 정원을 다시 확인한다.

## 내부 변경

`ChatPresenceRegistry`는 사용자 ID 대신 membership ID로 상태를 저장한다.
각 상태가 사용자·방·연결·구독·독립 만료 시각을 보유한다.
`hasCapacity`는 예약/유예를 포함한 계정을, `connectedCount`는 실제 연결이 있는 계정을 센다.
같은 방에 참여나 연결이 늘어도 실제 계정 수가 같으면 인원 이벤트와 version은 증가하지 않는다.
다른 방의 연결·구독·인원 version은 유지한다.

같은 membership의 재예약은 만료 시각을 연장하지 않는다.
다른 사용자·방으로 기존 membership 상태를 덮어쓰는 요청은 거절한다.
기존 참여 확인과 삭제에도 membership의 사용자 소유권을 유지한다.

기존 `synchronized`와 `exclusive` 임계 구역에서 정원 확인→DB 전환→예약을 순서대로 수행한다.
`reserve`는 승인된 참여를 등록하는 내부 메서드이며 정원 확인 없이 외부에서 단독 입장에 사용하면 안 된다.
입장 서비스와 CONNECT의 기존 호출 순서는 변경하지 않았다.

## 범위와 적용

REST·STOMP의 필드·오류 코드·DB 스키마는 변경하지 않는다. Flyway migration과 FE 변경은 없다.
현재 서버 메모리를 사용하는 단일 서버 구조다. 분산 정원 보장이나 성능 개선을 구현한 작업은 아니다.

B4 전에는 REST 입장이 여전히 사용자당 활성 DB 참여 하나를 조회한다.
B3만 배포해서 기기별 지역 입장이 완성되지는 않으며, sid 쓰기를 수동으로 활성화하지 않는다.
지역 이동·탭별 나가기·인증 세션별 로그아웃·계정 이력 조회는 각 후속 작업에서 바꾼다.
동일 membership을 종료하면 그 membership의 모든 연결이 닫히는 기존 동작은 유지된다.

적용 후 예약 25계정/26번째 거절, 같은 계정 추가 연결, 일부 연결 종료 후 인원 유지, 마지막 연결 종료 시 인원 감소를 확인한다.
B4 이후 여러 활성 membership이 생긴 데이터에는 이전 사용자 단일 상태 구현으로 단순 롤백하지 않는다.
연결과 신규 입장을 멈추고 후속 버전의 데이터 처리 계획과 함께 복귀해야 한다.
이번 작업에서 운영 DB 변경·배포·push·PR 등록은 수행하지 않았다.

## 검증

원본 포맷 및 컴파일 작업을 제외한 Checkstyle main/test는 통과했다.
원본 `compileJava`는 기존 `AuthExceptionHandler`의 누락 `AuthSessionController`·`LoginQueueController` 참조로 실패한다.
제품 인증 코드는 수정하지 않았다.

격리 사본 `/private/tmp/meomuneum-b3-verify-x9023nur`에서 누락된 두 import와 advice 대상만 제외하고,
누락 `LoginQueueAdmissionScheduler`를 참조하는 auth 테스트 디렉터리를 제외했다.
나머지 제품 코드·B3 테스트는 원본 그대로 검증한다. 이 결과를 원본 전체 빌드 성공으로 취급하지 않는다.

자동 검증 범위:

- 같은 방의 복수 membership·복수 연결 중복 제거, 정원 25에서 기존 계정 추가 허용/신규 계정 거절.
- 다른 방의 독립 자리·구독·이벤트·version, 참여 일부 종료 후 나머지 연결 유지.
- 독립 예약 및 유예의 정확한 30초 만료, 재시도에 의한 만료 연장 방지.
- 기존 24계정에 같은 계정의 추가 참여 20개와 신규 계정 20개가 경합할 때 총 25계정 제한.
- MySQL·실제 WebSocket에서 같은 계정의 두 방·세 membership 연결, 정원 1에서 중복 참여 허용,
  한 참여 종료 후 남은 연결의 메시지 전송과 다른 방 연결 유지.

실제 서버의 복수 membership은 B2의 sid 컬럼을 사용한 테스트 fixture로 생성한다.
B4의 REST 생성·sid 소유권 검증·기기별 이동을 검증한 결과가 아니다.
실제 단말·다중 서버·운영 데이터 규모의 부하 검증도 포함하지 않는다.

실행 결과: 전체 160개, 실패 0개, 오류 0개, 조건부 제외 1개.
원본과 격리 사본의 변경 Java 파일 3개가 동일함을 확인했다. 결과 XML과 집계는 `build/b3-capacity-verification/`에 보존한다.
